# 工单门禁与诚实声明规范

改编自 harness 工程（E:/code/guifan/2）的核心思想，配合 `scripts/gates/` 的校验脚本使用。这些规则写进工单处理流程，机器可判定的部分跑脚本，判断类规则靠自觉执行 + 日终反馈检查。

## 一、总原则

1. **门禁 PASS ≠ 业务 PASS**：脚本只校验"声明结构诚实"（有没有写入口/命令/断言/证据），业务结论永远来自真实运行验证。
2. **四轴分离记录**：execution（执行了吗）/ evidence（证据齐吗）/ documentation（文档同步了吗）/ human_decision（人工确认了吗）分开记录，不许互相顶替。
3. **状态降级必须带理由**：PASS 变 PARTIAL、DONE 重开，都要记录原因，不许无声变化。

## 二、入口确认双证（开工前）

改动前必须拿到两个证据，缺一标 NEEDS_REVIEW：
- **目标证据**：从需求原文到目标页面/API/函数的映射链（需求说改哪，代码在哪）
- **代码绑定证据**：确认该入口真的承载该业务（有调用链/路由/菜单记录佐证），防止改了没人用的死代码

## 三、改动契约（change contract）

M/C 级工单开工前写清（可并入方案书）：
```yaml
confirmed_goal: 已确认的目标（用户原话+复述）
target_entry: 目标入口（文件:行 / 路由 / 页面）
reproduction_status: 已复现 / 未复现(新功能)
expected_assertions: 预期断言（含至少一条反例断言）
in_scope: 本次改什么
out_of_scope: 明确不碰什么
```

**用户纠正即作废**：中途用户说"我说的不是这个"，本契约作废（SCOPE_INVALIDATED），已做的分析标记禁止复用，重新确认后再动。

## 四、自适应调查门禁（修 bug 时）

- 简单问题（一眼定位）→ 直接修
- 复杂问题 → **假设驱动**：每轮列 事实(O) / 假设(H) / 证伪方法 / 下一步探针，**连续两轮假设无新事实即停止**，向用户汇报卡点而不是继续猜
- 时间盒：5 分钟一个检查点、20 分钟单项上限、同路径两次无新证据换路径

## 五、共享业务规则归一

多个入口用到同一条业务规则（如"返投项目得分×0.7"、权限校验、状态流转）必须收敛到**一个共享方法/工具类**，各入口只留薄适配。发现第二处复制粘贴实现即为门禁失败。

## 六、测试计划一致性自查（7 条，测试角色用）

1. 目标链映射：每个验证项能追溯到需求/改动点
2. 请求形状：构造的入参与真实调用一致（字段/类型/单位，如能见度米 vs 公里）
3. 响应语义：断言的是业务语义，不只是 HTTP 200
4. 业务断言：至少一条正向 + 一条反例（C 级强制）
5. 证据通道：结果怎么留证（日志/截图/报文路径）
6. 路径语义：测的是目标入口，不是相似入口
7. 状态门：五态填写完整，TEST_BLOCKED 要写阻塞原因

## 七、总结的证据清单（evidence manifest）

写项目总结/日终反馈时，每个信息来源声明"支持什么结论"，**排除项显式列出**（"本次未运行生产验证，生产结论为 NOT_RUN"）。事实四分类：
- observed（直接看到）/ confirmed（已验证）/ inferred（推断，标注依据）/ pending（待确认）

禁止"生成了总结"被当成"验证了业务"。

## 八、知识入库门槛（solutions.md 用）

- **NO_CANDIDATE 是正常结果**：不因任务复杂就硬造经验条目
- 一次解决 → 最多标 CANDIDATE（条目标注"单次"）
- 升级为正式条目需满足其一：同类问题重复出现 / 跨项目再现 / 高严重度事故复盘 / 可测量收益
- 最终入库（写进 solutions.md）需人工（用户）确认过

## 九、S/M/C 与动作风险双轴独立

工单复杂度（S/M/C）和动作风险（如直接改生产库 = 高风险）是**两条独立的轴**，禁止机械换算——S 级工单也可能因执行风险高而需要额外确认。
